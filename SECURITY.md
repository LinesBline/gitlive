# Security model

gitlive turns a `git push` into a live process on hardware the owner
controls. This document says, plainly, what is protected, what each
signature means — and what it does **not** mean.

## Trust anchors (one key, one owner)

- **Owner manifest key** (Ed25519, generated by `gitlive manifest keygen`):
  signs app manifests, deploy receipts, member shares, and the attestation
  envelopes exported by `gitlive attest`. It is the single human trust
  anchor. Guard the private key (mode 600; offline media recommended).
- **Node key** (per machine): identifies a node in the mesh. A node key
  proves which *machine* spoke; the owner key proves *who* authorized it.
- **Storage key** (per machine): encrypts app data at rest (AES-256-GCM).
  Optional passphrase wrapping enables duress mode (see below).

## What each signature guarantees

| Signature | Proves | Does NOT prove |
|---|---|---|
| Signed manifest (`gitlive manifest sign`) | the owner authorized THIS code+dependency closure | that the code has no bugs |
| Deploy receipt (`refs/tags/gitlive/deploys/*`) | THIS commit deployed, with THIS outcome and closure, signed by the owner | that the machine wasn't compromised after signing |
| `gitlive attest` envelope (DSSE + in-toto/SLSA) | the deploy provenance is the owner's — verifiable with only the public key | package provenance (who built which binary) |
| Member share signatures | the shares came from the owner | that a member can't be coerced |

**The honest boundary:** deploy provenance proves what ran, where, and
who authorized it. It cannot prove the source code does what it claims —
that is the signed manifest's job, and the two are designed to verify
together.

## Threat model — ranked, honest

1. **Accidental loss** (deleted data, dead disk) — answered by `gitlive
   backup` (verified restic snapshots, receipted). A backup that cannot be
   verified is a wish, not a backup.
2. **Unsigned code drift** (someone/something edits the repo) — answered by
   the pre-receive manifest gate: unsigned or stale signatures are rejected
   before anything runs, and the refusal is audited.
3. **A compromised machine** — partially answered: deploy receipts stay
   valid for HISTORY (what happened), but a live compromise can deploy new
   signed-looking things only with the owner key, which should not live on
   that machine.
4. **Coercion** (someone forces the owner to act) — answered by design:
   duress passphrases (prefix `!`) shred keys irreversibly; the dead-man
   switch shreds when the owner cannot check in. Both are irreversible BY
   DESIGN and log every event. Restore-after-forced-shred is deliberate:
   the owner regains from their own distributed shares later; the coercer
   gets nothing from one machine.
5. **A malicious network or relay** — relays and entries are dumb plumbing:
   they see ciphertext (replicas hold ciphertext only) and cannot forge
   receipts without the owner key.

## Engineering guarantees

- **Zero runtime dependencies** (Node built-ins only) — no supply chain to
  compromise at runtime.
- **Zero telemetry / zero call-home** — nothing leaves the machine. The
  dashboard's fonts are SELF-HOSTED (bundled in `control/fonts/`, OFL,
  served same-origin): zero third-party requests of any kind, so no CDN
  ever sees a dashboard visitor.
- **No secrets in URLs** — the entry relay's token rides headers, never
  query strings (URLs leak into access logs; headers do not).
- **No hostnames in public artifacts** — the node identity and the SLSA
  builder.id use the mesh handle, never `os.hostname()`.
- **Web hygiene on every response** — `nosniff`, `no-referrer`, and a
  CSP pinning scripts/styles/fonts to the origin (inline allowed: the
  single-file dashboard makes it inherent), `frame-ancestors 'none'`.
- **Auth abuse is slow and audited** — identical error copy (no username
  oracle), 10-fail/10-minute lockout on login, every refusal logged.
- **Test battery as continuous proof** — every security-adjacent behavior
  (gates, receipts, shares, duress, dead-man, attestation, rate limits)
  is covered by the disposable suites in `tests/`.

## Reporting

gitlive is distributed privately. Report security issues through the
channel you received gitlive from. Include: version (`gitlive --version`),
what you observed, and a minimal reproduction. Public disclosure policy
will follow the first public release.

## Information boundaries (v4.0.1 audit)

gitlive is self-hosted, so "data protection" mostly means: the machine must not
publish its owner's business by accident. The boundaries, each pinned by
`tests/leak.test.js`:

| Surface | Rule |
| --- | --- |
| Agent ledger, timeline, digest | Credentials are stripped **before** a receipt is written, not on display |
| Error responses | Credentials stripped at one central boundary; paths kept (the owner needs them) |
| Support bundle | Identifiers masked by default; explicit `?full=1` for the owner's copy; payload says which |
| Weekly report | Identifiers masked by default; `gitlive report --no-redact` for the full one |
| Access log | Method, path, status, duration, request id — **never** a query string (paths, tokens) |
| `/health` | Status only: no names, no paths, no addresses, no handles |
| Dashboard | CSP `default-src 'self'` + `frame-ancestors 'none'`, no framing, no referrer, no sniffing, no third-party asset |
| DNS / entry / node tokens | Never returned by any endpoint; used server-side only |
| Peer announcements | Node identity + public key + endpoints; no app names, no paths |
| Outbound | Only where the owner asks (publish a name, request a cert, join a mesh) plus two check-ups that `GITLIVE_OFFLINE=1` disables |
| Shipped files | **No marker of the building machine** (home dir, user name, address) in anything `npm pack` includes |

The redactor's one deliberate asymmetry: **secrets are always stripped,
identifiers are masked only where the artifact is meant to leave the machine.**
An error the owner reads on their own screen keeps the path they must fix.

To report a leak: open an issue with the request id (every response carries
`x-request-id`, and the matching line is in `~/.gitlive/control/access.log`) and
the support bundle — which is masked by default, so it is safe to attach.
